Facial Recognition:
How It Actually Works

I used facial recognition as part of my walk-away lock project. Here's what I learned going beyond the library — encodings, distance matching, and where the system can fail.

The Problem It Was Solving

My walk-away lock already used Mediapipe to detect when someone left the webcam frame. But that only solved half the problem. When someone returned, the screen should only unlock for me — not whoever happened to sit down. That meant I needed identity verification, not just presence detection. Those are two different things.

I reached for the face_recognition library (built on top of dlib), but before I could use it properly I needed to understand what it was actually doing — because if I didn't understand the failure modes, I couldn't make it reliable.

Step 1: Detection vs Recognition

These two terms get conflated a lot, but they're distinct steps:

  • Detection — is there a face in this image? Where is it?
  • Recognition — whose face is it?

Detection comes first. The library uses a HOG (Histogram of Oriented Gradients) detector by default, which looks for gradient patterns in pixel intensities that match the shape of a face. It returns bounding box coordinates — top, right, bottom, left — for each face it finds. 

import face_recognition
import cv2

frame = cv2.imread("frame.jpg")
rgb   = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)

# Returns list of (top, right, bottom, left) tuples
locations = face_recognition.face_locations(rgb)

Step 2: Encodings — The Key Concept

This is where it gets interesting. Once a face is detected, the library passes the region through a deep neural network that converts it into a 128-dimensional vector — called an encoding. Think of it as a numerical fingerprint for that face.

The same person, photographed on different days, in different lighting, at slightly different angles, will produce encodings that are close to each other in that 128-dimensional space. Different people produce encodings that are far apart.

# Encode a known face (done once, saved to file)
known_image    = face_recognition.load_image_file("me.jpg")
known_encoding = face_recognition.face_encodings(known_image)[0]

# Encode a face from a live frame
live_encoding = face_recognition.face_encodings(rgb, locations)[0]

Step 3: Distance Matching

To decide whether the live face matches the known face, you calculate the Euclidean distance between the two 128-dimensional vectors. Smaller distance = more similar faces. 

distance = face_recognition.face_distance([known_encoding], live_encoding)[0]

# Typical threshold: 0.6
# Below 0.6 = likely same person
# Above 0.6 = likely different person
is_match = distance < 0.6

Why 0.6? It's the empirically derived default that balances false accepts vs false rejects for most use cases. You can lower it (stricter — fewer false accepts, more false rejects) or raise it (looser). For my lock, I used 0.55 to reduce the chance of unlocking for someone else.

What I Actually Had to Debug

Lighting changes wrecked early results

My enrolled photo was taken in daylight. Evening testing with artificial light produced noticeably different encodings — distances were creeping toward 0.58–0.62. Fix: enroll multiple reference images across different lighting conditions and use compare_faces against all of them, accepting a match if any pass.

Glasses changed the encoding significantly

Taking my glasses off (or putting them on) during testing pushed distance above the threshold. The network is trained to encode eye region features heavily, so eyewear matters more than you'd expect.

Frame rate vs accuracy tradeoff

Running face_encodings() on every frame is expensive. At 30fps this pegged one CPU core. Solution: only run recognition every 5th frame, and cache the last result in between. Good enough for a lock screen — the delay is imperceptible. 

frame_count = 0
last_result = False

while True:
    ret, frame = cap.read()
    frame_count += 1

    if frame_count % 5 == 0:   # only process every 5th frame
        last_result = check_identity(frame)

    if last_result:
        unlock_screen()

Security Perspective

The obvious attack on any face recognition system is a photo or video replay — holding up a photo of the enrolled person to fool the camera. The face_recognition library has no liveness detection built in. For a production system this matters a lot. For my threat model (protecting against someone who sits down at my desk opportunistically) it's out of scope — they won't have a photo of me to hand.

More serious systems solve this with:

  • Depth sensors (infrared) — used in Face ID and Windows Hello
  • Blink detection — check for natural eye movement
  • Challenge-response — ask the user to look left/right/smile

What I'd Do Differently

If I built this again I'd store the encoded vectors rather than re-encoding the reference image on every startup — it's a small but unnecessary compute cost. I'd also add a proper enrollment flow with 5–10 reference images captured automatically at startup to improve robustness across conditions.
